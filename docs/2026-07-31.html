LLMs Have a Fundamental, Unfixable Security Flaw, Researchers Argue
A paper presented at ICML this month makes a provocative but well-reasoned claim: large language models cannot be made fully secure against prompt injection attacks, not because of implementation bugs, but because of how they fundamentally work. The core problem is that LLMs process instructions and data through the same channel — text — so there's no architectural way to enforce a hard boundary between 'things the user told me to do' and 'things I read in a document.' Prompt injection, where malicious instructions are embedded in content the model processes, is therefore not a patch-and-move-on vulnerability but a structural one. The researchers argue this has huge implications for any agentic deployment where the AI reads external content — emails, documents, web pages — and then takes actions. Simon Willison highlighted a related attack this week: a researcher named Håkon Måløy demonstrated a self-replicating prompt injection worm that spreads through Microsoft Word documents via Copilot. An attacker embeds instructions in a document; when Copilot processes it, it interprets those instructions as user commands and propagates them to new documents. The worm angle is particularly nasty because it scales without attacker involvement. This body of research collectively suggests the industry needs to stop treating prompt injection as a content moderation problem and start treating it as a fundamental architectural constraint. Practically, this means any AI system that reads untrusted input and takes consequential actions needs defense-in-depth at the system level — sandboxing, capability restrictions, human-in-the-loop checkpoints — not just better prompting. The paper doesn't offer a silver-bullet fix because, by its own argument, there likely isn't one.

New MCP Specification Goes Stateless to Unlock Enterprise Adoption
The Model Context Protocol (MCP) — the standard for connecting AI models to external tools and data sources — got a significant spec update targeting the main reason enterprises haven't adopted it at scale: stateful session management. The previous MCP design required persistent connections, which is fine for local developer tooling but breaks badly in cloud environments where you're load-balancing across many servers. The new stateless design means any server can handle any request without needing to know about previous interactions, which maps much more naturally to standard HTTP infrastructure. Alongside the architectural change, the MCP governance team announced a new deprecation policy: features won't be removed suddenly. That's a small thing that matters enormously to enterprise procurement teams who can't adopt a protocol that might break their integrations on short notice. MCP has been gaining fast adoption among developer tools — Claude, ChatGPT, and various IDEs now support it — but enterprise deployment has lagged because of exactly these concerns. The stateless redesign is essentially bringing MCP in line with how REST APIs work, which lowers the barrier for any backend team that already knows how to run web services. For AI engineers, this is the spec update that probably unlocks MCP for production internal tooling deployments, not just local prototyping. The protocol is positioned as a universal connector between AI models and everything else, so getting the enterprise story right matters for the entire ecosystem. Simon Willison published a tutorial this week on adding custom MCP servers to both Claude and ChatGPT, which gives you a sense of where the developer workflow is currently.

Quantum Computing Achieves Verifiable Results Beyond Classical Reach
Researchers have made progress on one of quantum computing's most philosophically tricky problems: how do you verify that a quantum computer's output is correct when classical computers can't reproduce the calculation to check it? This is sometimes called the quantum verification problem, and it's not merely academic — if you can't trust the results, you can't use the machine for anything important. Ars Technica's coverage describes three distinct approaches to the problem, each with different tradeoffs. The first relies on cross-checking results from multiple independent quantum systems; the second uses mathematical proof structures that let a classical verifier check quantum work without re-running it; the third involves constructing problems where correctness can be verified independently of the computation itself. The fact that multiple viable approaches now exist is genuinely encouraging — it means the field isn't stuck waiting for one solution. This matters because quantum advantage claims have been contested for years precisely because critics could argue the results weren't reliable; having verifiable quantum computation removes that objection. Simultaneously, qubit technology continues to diversify, with new quantum dot options and diamond nitrogen-vacancy approaches both showing progress in separate research this week. The quantum computing field in mid-2026 looks less like a single horse race and more like a Cambrian explosion of approaches — superconducting qubits, trapped ions, photonic systems, quantum dots, diamond vacancies — all advancing in parallel. For engineers tracking this space, the verification progress is probably the more practically important story than any individual qubit milestone.
